# ADR-004. Стилизация: styled-components без inline-CSS

**Статус:** принято · **Этап:** step/1

## Контекст

Задание запрещает inline-CSS и UI-библиотеки (MUI, Ant), а styled-components отмечены как плюс.
При этом часть стилей зависит от данных: цвет индикатора эффективности (0–100), выделение строки,
уровень вложенности, состояние соединения.

## Решение

- `styled-components` v6 с типизированной темой (`app/styles/theme.ts`, `styled.d.ts`) и
  `GlobalStyle`, где глобально уважается `prefers-reduced-motion`.
- Запрет inline-CSS закреплён линтером: `react/forbid-dom-props` и `react/forbid-component-props`
  для пропа `style` — ошибка сборки, а не договорённость.
- Стили, зависящие от данных с большим числом значений, идут **через data-атрибуты и бакеты**:
  индикатор эффективности получает `data-bucket="low|medium|high"`, а CSS описывает три селектора.
  Так не возникает класс на каждое из 101 значения, что было бы при интерполяции значения в CSS.
- Булевы и малочисленные состояния (`$selected`, `$open`, `$variant`) передаются transient-пропами:
  число порождаемых классов ограничено.

## Альтернативы

- **CSS Modules.** Нулевой runtime, но тема и динамические состояния требуют дублирования
  в className-логике; плюс задания за styled-components не получить.
- **CSS custom properties через `style={{'--x': ...}}`.** Технически удобно для динамики, но это
  тот самый inline-CSS, который запрещён.
- **Tailwind.** Быстро, но это утилитарные классы в разметке; для тестового задания на React +
  styled-components неуместно.

## Последствия

- `+` ~11 КБ gzip за runtime; типизированная тема; ноль inline-стилей, что проверяется на CI.
- `−` Runtime-генерация классов; для больших таблиц важно не интерполировать уникальные значения.
