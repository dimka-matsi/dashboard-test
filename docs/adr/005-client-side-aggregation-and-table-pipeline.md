# ADR-005. Агрегация на клиенте и конвейер производного состояния таблицы

**Статус:** принято · **Этап:** step/2

## Контекст

API отдаёт только собственные метрики узлов. Таблица должна показывать суммарные показатели
(узел + все потомки), среднюю эффективность, взвешенную по численности, сортировку по любому
столбцу, фильтр с дебаунсом и выделение узла в дереве. Требование: агрегация считается один раз
после загрузки и мемоизируется; на этапе 3 добавится инкрементальный пересчёт по патчам.

## Решение

1. **Агрегаты считает клиент** из плоского массива: `computeAggregates(tree)` за O(n) обратным
   pre-order обходом (дети всегда раньше родителей). Формулы — в `docs/data-model.md`.
   Взвешенное среднее хранится как пара (`weightedPerformanceSum`, `totalHeadcount`), а не как
   готовое число: так родитель складывает числители и знаменатели детей точно, деление делается
   один раз. При `totalHeadcount = 0` среднее — `null`, в UI прочерк.
2. **Единица мемоизации — модель** `OrgModel = { tree, aggregates }`, строится `useMemo` на ссылку
   данных из кэша. Structural sharing гарантирует, что одинаковый ответ не меняет ссылку.
3. **`aggregateNode(tree, aggregates, id)`** пересчитывает один узел из собственных значений и
   агрегатов детей. Полный пересчёт — это `aggregateNode` для каждого узла; инкрементальный
   (этап 3) — `aggregateNode` для узла и его предков. Одна функция, два режима — инвариант
   «инкрементально = полностью» проверяется тестом.
4. **Таблица — плоский список** с конвейером `buildRows(model) → filterRows(debounced) → sortRows(sort)`,
   каждый шаг в своём `useMemo`. Ввод в фильтр обновляется мгновенно, применение — через 250 мс.
   Сортировка стабильная: при равенстве сохраняется порядок дерева; `null` всегда в конце.
5. **Семантика сортировки.** Клик по новому столбцу — по возрастанию; клик по текущему — без
   изменений; двойной клик — обратный порядок. Двойной клик приходит после двух одиночных,
   и если бы одиночный клик переключал направление, результат зависел бы от скорости клика.
   Сброс — отдельной кнопкой. Для клавиатуры: Enter — сортировать, Shift+Enter — обратный порядок.
6. **Выделение** хранится в `Dashboard` и передаётся в обе панели. Дерево раскрывает предков
   выбранного узла и прокручивает к нему; на узком экране выбор строки переключает на дерево.
   Обе панели остаются смонтированными (`hidden`), чтобы раскрытие и фильтр не терялись при
   переключении.

## Альтернативы

- **Агрегировать на сервере.** Проще клиенту, но противоречит заданию (агрегаты — часть
  клиентской логики с unit-тестом) и делает live-патчи тяжелее: пришлось бы пересылать агрегаты
  всех предков.
- **Считать агрегаты в компоненте строки.** Пересчёт при каждом рендере и O(n²) на таблицу.
- **Иерархическая таблица (tree grid).** Красиво, но сортировка «по любому столбцу» внутри
  уровней теряет смысл сравнения дивизиона с командой; плоский список с колонкой «Уровень»
  честнее для аналитики.
- **Хранить `avgPerformance` и складывать средние.** Неверно математически (среднее средних) —
  поэтому числитель и знаменатель хранятся раздельно.

## Последствия

- `+` O(n) на загрузку, O(глубина) на патч; точная целочисленная арифметика сумм.
- `+` Чистые функции без React — тестируются напрямую.
- `−` Для десятков тысяч узлов понадобилась бы виртуализация строк; для орг-структуры
  на сотни узлов это не требуется.
