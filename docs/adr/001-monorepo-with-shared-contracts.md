# ADR-001. Монорепозиторий на npm workspaces с общим пакетом контрактов

**Статус:** принято · **Этап:** step/1

## Контекст

По заданию нужны и клиент (React + Vite), и собственный mock-сервер (`GET /api/org-tree`, позже —
WebSocket и AI-разбор запросов). Оба конца должны одинаково понимать форму данных: узел орг-структуры,
патч live-обновления, структурированный фильтр поиска. Если описать схему дважды, она неминуемо
разъедется.

## Решение

Один репозиторий, три workspace-пакета через встроенные npm workspaces (без pnpm/turbo):

- `packages/contracts` — zod-схемы и выведенные из них типы. Пакет отдаётся как TypeScript-исходник
  (`exports` → `./src/index.ts`): Vite, `tsx` и `esbuild` транспилируют его сами, отдельный шаг сборки
  не нужен.
- `apps/server` — Node 22, `node:http` + `ws`, без фреймворка.
- `apps/web` — Vite + React 19 + styled-components.

Сервер и клиент импортируют одни и те же схемы: сервер валидирует входящие данные, клиент — ответы.
Общий lockfile, общие `eslint`/`prettier`/`vitest` в корне.

## Альтернативы

- **Два независимых проекта в одном репозитории.** Проще Dockerfile, но контракт дублируется.
- **pnpm workspaces / Turborepo.** Быстрее и мощнее, но для трёх пакетов это лишний инструмент,
  а проверяющему нужен ещё один менеджер пакетов.
- **Mock API как middleware Vite dev-server.** Одна команда запуска «из коробки», но в задании
  сервер нужен как отдельный сервис (Docker, nginx-прокси, WebSocket).

## Последствия

- `+` Одна схема на оба конца; изменение контракта ломает typecheck там, где его не учли.
- `+` `npm install` в корне ставит всё; `npm run dev` поднимает оба процесса.
- `−` Docker-сборка каждого сервиса использует корень репозитория как контекст (нужен общий lockfile).
- `−` Пакет-исходник нельзя опубликовать как есть; для внутреннего монорепо это не требуется.
