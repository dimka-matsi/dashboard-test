# ADR-008. AI-поиск: разбор на сервере, структурированный фильтр на клиенте, fallback по правилам

**Статус:** принято · **Этап:** step/4

## Контекст

Строка поиска должна принимать естественный язык («отделы с эффективностью ниже 50»),
а ответом должен быть структурированный фильтр, который применяет клиент; при неудаче —
текстовый поиск. Ключ языковой модели нельзя раскрывать в браузере, а проверяющий может
запускать проект без ключа вовсе.

## Решение

1. **Контракт фильтра** (`packages/contracts/src/search.ts`): `SearchFilter` с полями `text`,
   `levels`, `headcount`/`budget`/`performance` (диапазоны `min`/`max` по **суммарным** показателям),
   `within` (подстрока названия предка), `sort`, `limit`. Один и тот же zod-контракт валидирует
   ответ модели на сервере и ответ сервера на клиенте.
2. **Разбор — на сервере** (`POST /api/search/parse`), в два уровня:
   - **Языковая модель** через официальный SDK `@anthropic-ai/sdk`, если задан `ANTHROPIC_API_KEY`.
     Используется structured output (`output_config.format` с JSON Schema фильтра) — ответ
     гарантированно валидный JSON нужной формы; `effort: low`, таймаут `AI_TIMEOUT_MS`.
     Модель по умолчанию — `claude-opus-5`, переопределяется `ANTHROPIC_MODEL`.
   - **Правила** (`search/rules.ts`): детерминированный разбор русского и английского — уровни,
     метрики с порогами («ниже 50», «от 10 человек», «между 10 и 50 млн»), предок («в дивизионе
     Платформа»), «топ N»/«худшие», остаток запроса → подстрока названия. Работает без сети и
     ключей и покрывает типовые формулировки.
     Любая ошибка модели (сеть, лимит, таймаут, отказ, ответ вне схемы) → правила; ничего не
     распознано → `{ filter: null, source: 'none' }`. Ответ кэшируется по нормализованному запросу.
3. **Клиент** (`features/search`): одно поле ввода. Подстрока применяется сразу (дебаунс 250 мс);
   фраза из двух и более слов или с числом через 500 мс уходит на разбор (`TanStack Query`,
   `staleTime: Infinity` — повторный ввод той же фразы не порождает запрос). Полученный фильтр
   применяется функцией `applySearchFilter` и показан чипами с пометкой источника
   («AI-фильтр» / «фильтр по правилам» / «текстовый поиск»). Ошибка разбора или `null` →
   текстовый поиск по той же строке. Ручная сортировка пользователя имеет приоритет над
   сортировкой из фильтра.

## Альтернативы

- **Вызов модели из браузера.** Проще, но ключ утекает в клиент — неприемлемо.
- **Только правила.** Не «AI-фича» по духу задания, хотя именно правила обеспечивают работу
  без ключа; поэтому они оставлены как обязательный fallback, а не единственный путь.
- **Tool use с принудительным вызовом инструмента.** Работает, но structured output —
  каноничный способ получить JSON нужной формы; forced tool use к тому же недоступен на части
  новых моделей.
- **Server-side fallback на другую модель при отказе** (`fallbacks`, beta). Для парсера фильтра
  отказ модели маловероятен, а поведение при нём уже определено (правила); бета-параметр
  без возможности проверить его в среде разработки не добавлен намеренно.

## Последствия

- `+` Ключ модели никогда не покидает сервер; без ключа функция работает в урезанном виде.
- `+` Один контракт фильтра на три источника: модель, правила, клиентское применение.
- `−` Правила покрывают только предсказуемые формулировки; свободные формы требуют модели.
- `−` Запрос к модели добавляет задержку (сотни мс — секунды); UI на это время показывает
  результат текстового поиска и спиннер.
