# ADR-006. Live-обновления: WebSocket и версионированный протокол патчей

**Статус:** принято · **Этап:** step/3

## Контекст

Сервер поддерживает обновления в реальном времени; клиент должен применять патч без полного
рефетча, показывать индикатор соединения и восстанавливаться с экспоненциальным backoff.
Задание допускает WebSocket, SSE или эффективный поллинг, но в перечне документов явно назван
«контракт WebSocket-патча».

## Решение

**Транспорт — WebSocket** (`ws` на сервере, нативный `WebSocket` в браузере) на том же
HTTP-сервере, путь `/ws`; в dev проксируется Vite, в prod — nginx.

**Протокол** (`packages/contracts/src/live.ts`):

| Сообщение       | Направление   | Смысл                                                                 |
| --------------- | ------------- | --------------------------------------------------------------------- |
| `hello`         | S → C         | первым после подключения: `serverId`, текущий `seq`, период heartbeat |
| `patch`         | S → C         | изменения узлов, `seq` строго +1 к предыдущему состоянию              |
| `resync`        | S → C         | дослать пропущенное нельзя — клиент перезапрашивает снимок            |
| `ping` / `pong` | S → C / C → S | heartbeat                                                             |

Ключевые свойства:

1. **Абсолютные значения, не дельты.** Патч несёт новые значения полей — применение идемпотентно,
   повтор после ресинка ничего не ломает.
2. **`seq` — единый счётчик состояния.** Он же — версия снимка (`X-Org-Version` в ответе
   `GET /api/org-tree`) и часть ETag. Клиент применяет патч только если `seq = version + 1`;
   `seq <= version` — устаревший, пропускается; `seq > version + 1` — пропуск → ресинк.
3. **Курсор в URL подключения** (`/ws?serverId=…&since=…`), а не отдельным сообщением.
   Сервер досылает пропущенные патчи из кольцевого буфера синхронно в обработчике подключения,
   до того как клиент попадёт под широковещательную рассылку — порядок `seq` на проводе строгий,
   гонки «сначала новый патч, потом досылка старых» нет.
4. **`serverId`** меняется при рестарте сервера: старые `seq` несопоставимы → `resync`.
5. **Heartbeat** в обе стороны: сервер терминирует клиентов без `pong`, клиент считает
   соединение мёртвым после 2,5 периодов тишины и переподключается сам, не дожидаясь `onclose`.
6. **Backoff**: 500 мс × 2ⁿ до 30 с, джиттер ±30 %; сброс после `hello`. События `online`
   и возврат вкладки инициируют немедленную попытку. Пока канал не восстановлен после двух
   попыток, включается редкий поллинг снимка (15 с) как деградация.

## Альтернативы

- **SSE.** Проще (обычный HTTP, авто-реконнект `EventSource`), достаточно для одностороннего
  потока. Но встроенный реконнект не даёт управлять backoff и статусом, а `Last-Event-ID`
  пришлось бы всё равно дублировать своим курсором. Плюс задание ждёт WS-контракт.
- **Поллинг с ETag.** Без нового транспорта, но задержка равна периоду опроса, и «патч без
  рефетча» превращается в diff снимков на клиенте.
- **Полный снимок в каждом сообщении WS.** Проще протокол, но это и есть «полный рефетч»,
  только по другому каналу.

## Последствия

- `+` Патч ~200 байт против снимка ~10 КБ; порядок и полнота проверяемы по `seq`.
- `+` Любая рассинхронизация сводится к одному `GET` снимка — система самовосстанавливающаяся.
- `−` Nginx нужно настроить на upgrade и длинный `proxy_read_timeout`; heartbeat держит
  соединение живым сквозь прокси.
- `−` Структурные изменения (добавление/удаление узлов) в патч не входят: сервер их не
  генерирует, а клиент отбрасывает неизвестные id. Расширение — отдельный тип сообщения.
