# Модель данных

## Узел орг-структуры

`GET /api/org-tree` возвращает **плоский массив** узлов (`packages/contracts/src/org-node.ts`):

| Поле          | Тип              | Ограничения                           |
| ------------- | ---------------- | ------------------------------------- |
| `id`          | `string`         | непустой, уникальный                  |
| `name`        | `string`         | 1–200 символов                        |
| `parentId`    | `string \| null` | `null` — корень (дивизион)            |
| `headcount`   | `int`            | ≥ 0, собственная численность узла     |
| `budget`      | `number`         | ≥ 0, рубли, собственный бюджет узла   |
| `performance` | `number`         | 0–100, собственная эффективность узла |
| `updatedAt`   | `string`         | ISO-8601 (`2026-09-14T10:00:00.000Z`) |

Метрики узла — **собственные**, без потомков. У дивизиона и отдела они ненулевые (управленческий
персонал и его бюджет), поэтому агрегат узла = собственные значения + значения всех потомков.

Валидация на клиенте: `z.safeParse(OrgTreeResponseSchema, json)`. Один невалидный элемент делает
невалидным весь ответ — частично корректные данные показывать опаснее, чем не показывать.

## Дерево

Плоский массив превращается в индекс `OrgTree` (`apps/web/src/entities/org/model/build-org-tree.ts`):

```ts
interface OrgTree {
  nodes: Map<id, OrgNode>; // O(1) доступ
  children: Map<id, id[]>; // дети, отсортированы по имени (Intl.Collator 'ru', numeric)
  roots: id[]; // parentId === null
  depth: Map<id, number>; // 1 — дивизион, 2 — отдел, 3 — команда
  order: id[]; // pre-order обход: порядок строк таблицы «как в дереве»
  maxDepth: number;
}
```

Алгоритм: один проход для индекса и группировки детей, сортировка детей, итеративный DFS для
глубины и порядка. Сложность O(n log n) из-за сортировки.

### Проверки целостности

Схема гарантирует форму каждого узла, но не согласованность массива. Ошибки `OrgTreeError`:

| Код              | Условие                                        |
| ---------------- | ---------------------------------------------- |
| `duplicate-id`   | два узла с одним `id`                          |
| `missing-parent` | `parentId` указывает на отсутствующий узел     |
| `self-parent`    | `parentId === id`                              |
| `cycle`          | после DFS от корней остались непосещённые узлы |

Любая из них переводит экран в состояние ошибки — так же, как невалидная схема.

| ----- | --------- |

| 2     | Отдел     |
| 3     | Команда   |

## Алгоритм агрегации

Агрегат узла включает его собственные метрики и метрики **всех** потомков
(`apps/web/src/entities/org/model/aggregate.ts`):

```
totalHeadcount(v) = headcount(v) + Σ totalHeadcount(c),   c ∈ children(v)
totalBudget(v)    = budget(v)    + Σ totalBudget(c)
W(v)              = performance(v) · headcount(v) + Σ W(c)        — взвешенная сумма
avgPerformance(v) = W(v) / totalHeadcount(v),  если totalHeadcount(v) > 0, иначе null
```

- **Полный пересчёт** `computeAggregates(tree)` — O(n): массив `order` (pre-order) обходится
  с конца, поэтому к моменту обработки родителя агрегаты всех его детей уже посчитаны.
- **Один узел** `aggregateNode(tree, aggregates, id)` — O(число детей): собственные значения плюс
  агрегаты детей. Полный пересчёт — это `aggregateNode` для каждого узла; инкрементальный
  (этап 3) — для изменённого узла и его предков, O(глубина · ветвление).
- **Точность.** Суммы численности и бюджета — целые, взвешенная сумма — целая при целых
  `performance`; деление выполняется один раз в конце. Среднее средних не используется.
- **Нулевая численность.** Взвешенное среднее не определено → `null`, в таблице «—»,
  при сортировке такие строки всегда в конце.
- **Мемоизация.** Модель `{ tree, aggregates }` строится один раз на ссылку данных из кэша
  (`useMemo`); одинаковый ответ сервера ссылку не меняет (structural sharing).

Пример на фикстуре из тестов: дивизион А (4 чел., 80) → отдел А1 (3 чел., 90; команды 10 × 75
и 5 × 95) и отдел А2 (1 чел., 40; команда 8 × 30):

```
totalHeadcount(A) = 4 + (3 + 10 + 5) + (1 + 8) = 31
W(A)              = 320 + (270 + 750 + 475) + (40 + 240) = 2095
avgPerformance(A) = 2095 / 31 ≈ 67,6
```

## Строки таблицы

`buildRows(model)` разворачивает модель в плоский список в порядке дерева: имя, уровень, путь от
корня, три агрегата и `treeIndex` — стабилизатор сортировки. Далее `filterRows` (подстрока
по названию без учёта регистра, лишних пробелов и ё/е) и `sortRows` (стабильная сортировка,
`null` в конце). Каждый шаг мемоизирован отдельно.

## Контракт WebSocket-патча

Канал: `GET /ws` (Upgrade). Все сообщения — JSON, схемы в `packages/contracts/src/live.ts`
(`ServerMessageSchema`, `ClientMessageSchema`); клиент и сервер валидируют входящие сообщения.

### Сервер → клиент

```ts
{ type: 'hello',  serverId: string, seq: number, heartbeatMs: number }
{ type: 'patch',  seq: number, changes: NodeChange[] }
{ type: 'resync', seq: number, reason: 'server-restarted' | 'gap-too-large' | 'unknown-cursor' }
{ type: 'ping',   t: number }

NodeChange = {
  id: string,
  fields: { headcount?: int ≥ 0, budget?: number ≥ 0, performance?: 0..100 },  // новые значения
  updatedAt: string  // ISO-8601
}
```

### Клиент → сервер

```ts
{ type: 'pong', t: number }
```

Курсор возобновления передаётся в URL: `/ws?serverId=<id>&since=<seq>`.

### Версии и порядок

- `seq` увеличивается ровно на 1 при каждом патче. Снимок `GET /api/org-tree` несёт ту же
  величину в заголовке `X-Org-Version` (и `X-Server-Id`), ETag — `W/"<serverId>-<seq>"`.
- Клиент применяет патч, только если `seq = version + 1`. `seq ≤ version` — устаревший
  (например, повтор после ресинка), пропускается. `seq > version + 1` — пропуск → клиент
  перезапрашивает снимок (`invalidateQueries`), и версия выравнивается.
- Сервер хранит последние N патчей (`PATCH_BUFFER_SIZE`, по умолчанию 500). При подключении
  с курсором он досылает патчи `since+1 … seq` **синхронно, до включения клиента в рассылку**,
  поэтому порядок на проводе всегда строгий.
- `resync` приходит, когда дослать нельзя: другой `serverId` (рестарт), разрыв больше буфера,
  нечитаемый курсор. Клиент делает один `GET` снимка.

### Последовательность

```
клиент                                   сервер
  │── GET /api/org-tree ───────────────────►│  200, X-Org-Version: 41
  │── WS /ws?serverId=s1&since=41 ─────────►│
  │◄── hello {seq: 43} ────────────────────│  досылка синхронно:
  │◄── patch {seq: 42} ────────────────────│  ← из буфера
  │◄── patch {seq: 43} ────────────────────│  ← из буфера
  │◄── patch {seq: 44} ────────────────────│  ← live
  │◄── ping ───────────────────────────────│
  │── pong ────────────────────────────────►│
```

### Применение на клиенте

`applyNodeChanges(model, changes)` (`entities/org/model/apply-changes.ts`):

1. Для каждого изменения сравнивает новые значения с текущими; узлы без реальных изменений
   не трогаются, неизвестные `id` собираются в `unknownIds`.
2. Затронутые узлы и все их предки сортируются по глубине (глубокие раньше) и пересчитываются
   через `aggregateNode` — O(k · глубина · ветвление) для k изменённых узлов.
3. Возвращает новую модель (незатронутые объекты — те же ссылки) и карту реально изменившихся
   ячеек: собственные поля у узла, `totalHeadcount` / `totalBudget` / `avgPerformance` у него
   и предков. По ней ячейки получают подсветку с затуханием ~1,5 с.

Структурные изменения (добавление, удаление, перенос узла) в контракт патча не входят; для них
предусмотрен путь через `resync` и полный снимок.

## Структурированный фильтр поиска

`POST /api/search/parse` принимает `{ query: string }` и возвращает
`{ filter: SearchFilter | null, source: 'llm' | 'rules' | 'none', explanation? }`
(`packages/contracts/src/search.ts`):

```ts
SearchFilter = {
  text?: string,                                  // подстрока названия
  levels?: number[],                              // 1 дивизион, 2 отдел, 3 команда
  headcount?: { min?: number, max?: number },     // суммарная численность
  budget?: { min?: number, max?: number },        // суммарный бюджет, руб.
  performance?: { min?: number, max?: number },   // средняя эффективность 0–100
  within?: string,                                // подстрока названия предка
  sort?: { column: 'name' | 'level' | 'totalHeadcount' | 'totalBudget' | 'avgPerformance',
           direction: 'asc' | 'desc' },
  limit?: number,                                 // первые N после сортировки
}
```

Клиент применяет фильтр к строкам таблицы (`features/search/apply-filter.ts`): текст → уровни →
диапазоны по суммарным показателям → предок → сортировка → `limit`. Строки без средней
эффективности (нулевая численность) не проходят условие по `performance`.
